# Live runs: smoke test, live evaluation, recorded bundles

Everything in milestone 3 is built and tested on the fake model client. These are the manual steps that need the
Foundry project and the model deployments: gpt-5-mini for now, because the trial subscription has no GPT-6 Luna quota
(decision 19). They spend real (small) amounts of money; every call is logged to `runs/llm_usage.jsonl` and capped by
the budgets in `.env`. Set `PITCHSIDE_PRICE_MODEL` to the model behind the deployments (`gpt-5-mini`, or `gpt-6-luna`
if Luna quota is granted), so the log prices the calls correctly.

## 1. Smoke test (a few cents at most)

```powershell
az login
# .env: PITCHSIDE_LLM=foundry, FOUNDRY_ENDPOINT, MODEL_INTERPRETER/EXPLAINER/VERIFIER/PERSONALIZER (all the
#       gpt-5-mini deployment), PITCHSIDE_PRICE_MODEL=gpt-5-mini, PITCHSIDE_REASONING_EFFORT=low
uv run python scripts/smoke_foundry.py
```

It reports which API path works (Responses or Chat Completions), makes one call per role, checks that the budget
guard refuses before sending, and runs one goal through the whole agent pipeline. Check in its output:

- step 4 (one explainer request with the real cap, no retry) prints `OK  valid JSON`;
- step 5 ends with `OK  verified model narrative`;
- step 6 says `ok` for every role. `TOO TIGHT` names the `PITCHSIDE_MAX_OUTPUT_<ROLE>` value to set: a reply hit the
  cap, or the largest output (reasoning included) left less than twice the room. "Output cap reached while
  reasoning" means the model spent the cap thinking: raise the cap or lower the reasoning effort;
- a `bad_request` hint, if any (set `PITCHSIDE_REASONING_EFFORT=off`, then try `FOUNDRY_API=chat_completions`).
  gpt-5-mini accepts `minimal`, `low`, `medium` and `high` (not `none`; the settings refuse it at startup). With
  `off` it reasons at its default, `medium`, which costs more.

Record the API path, the measured cost of steps 4-5 and the step 6 table in `docs/DECISIONS.md`.

## 2. Live evaluation (about $2.10-2.30 estimated at gpt-5-mini prices, 20 matches)

Held-out seeds 201-205, all four storylines. Prompts were written against seeds 1-40 only.

```powershell
$env:PITCHSIDE_LLM = "foundry"
uv run pitchside eval-agents --seeds 201-205 --live
```

`--live` is required on top of `PITCHSIDE_LLM=foundry`, so a stray command never spends money. Output goes to
`runs/eval/<eval id>/`: `report.txt` (the same metrics as offline, labelled LIVE), `summary.json`, one bundle per
match, and `spotcheck.md`, a sample of 20 shown claims with their evidence. Label each one supported or
unsupported by hand: that is the honest "after the verifier" number, because the deterministic gate makes the
automatic one 0 by construction.

Then:

- replace the estimated cost in the README and decisions 14 and 19 with the measured cost per match;
- put the live numbers in the README next to the offline ones, labelled as live, with the seeds;
- if quality falls short, improve the prompts (decision 1: no larger model), re-run on seeds 1-40, and only then
  re-run the held-out seeds once.

To measure how much the verifier catches from a real model on purpose-made bad drafts, add `--inject-bad 0.2`
(corrupts the first draft of 20% of jobs after the model wrote it; the model call is real and billed).

## 3. Recorded bundles for the demo

Keep the match budget at $0.25 (the default; about twice the estimated $0.12-0.13 of a storyline match on

$env:PITCHSIDE_LLM = "foundry"

- **Timeout charges are worst-case estimates.** A timed-out call (explainer or personalizer, 24 in all) returns no

  worst case.
- **All figures are logged estimates, not the bill.** They come from token counts and the price table. Azure Cost

Notes on the classes:

- **Wrong possession cause.** In 201-210 most wrong causes came from the ledger's own label ("after winning the
  ball" for every possession). Decision 23 made the label name the real cause.
- **Combined figure read as per-team.** In 201-205 the labels said "match", so this error showed up as a scope error.
- **Present-tense score in a recap.** The recap ledger copies the goal's `goal_margin` label ("it is 1-0: …") without
  changing its tense. The checker accepts the claim because 1-0 was a score of the match. 206-210 had no "it is"
  label, and the scan found no such claim there, but the scan only looks for present-tense forms.
- **Borderline claim.** 301-305 #7 ("Aurora Rovers have 66.2% possession, and Ironvale Athletic have 0 shots in this
  spell") was drafted as NEEDS HUMAN and labelled supported in review. The 66.2% is a 5-minute share (their match
  possession was 52.7%), and only the sentence-final "in this spell" names the window.

**Known residuals** (as measured on `2a208c4`)

- **Possession cause in Spanish persona texts.** In 301-305, 55 of 670 cause mentions in persona texts are wrong and
  Spanish: the personalizer writes "recuperar la posesión" (won the ball back) for restarts, and "fuera de juego"
  (offside) for out of play. Two more wrong mentions are English. The checker does not check how possession began.
- **A verifier false rejection and the wrong-window rewrite.** In one surge (301-305, end_to_end_0302
  pressure_surge:1) the verifier rejected "in this spell", taking the detection minute as the spell's start. The
  rewrite that was shown says "In the 46:49–51:49 window Ironvale Athletic had 4.0 pressures per minute", but that
  rate covers 48:49–51:49.
- **Present-tense score in a recap** (3 claims in 301-305, error class above). Decision 25 adds the recap's own
  score and a checker rule for it; validated offline only, not measured live.
- **Not addressed by Commit D** (decisions 24-26): no semantic check of persona texts; combined figures given to one
  club in persona texts; the Spanish possession wording above; tone words ("rattles", "gilt-edged", "spurns");
  "puts … ahead" at the whistle is a prompt rule only. The woodwork, body-part and record phrases are now rejected
  deterministically (decision 26), also validated offline only.
