# Decision log

Lightweight record of decisions that shape the architecture, models, cost or how we evaluate.
Newest entries at the bottom. Each entry: date, decision, why, and what we rejected.
Add an entry in the same commit as any change that touches these areas.

## 1. One small model for every agent: GPT-6 Luna, no Sol (2026-10-18)

**Decision:** every agent role (interpreter, explainer, verifier, personalizer) runs on GPT-6 Luna in Microsoft Foundry (Global Standard, Sweden Central), each role reading its own deployment name from an env var.
**Why:** cost. Luna is $0.10 in / $0.01 cached / $0.50 out per 1M tokens, and a deterministic detector keeps us to about 30 model calls per match.
**Rejected:** Sol or any larger model, even for the explainer. If quality falls short we improve prompts (compact structured evidence, tight output format, examples) and lean on the verifier.
**Update (decision 19):** the trial subscription has no Luna quota, so gpt-5-mini runs every role for now; Luna is the target again if quota is granted.

## 2. Microsoft Agent Framework calling model deployments directly (2026-10-18)

**Decision:** agents are built with Microsoft Agent Framework and call the Foundry model deployments directly, authenticated with Entra ID.
**Why:** Foundry Agent Service pricing is unconfirmed and we need to keep the cost near zero until Nov 10.
**Rejected:** Foundry Agent Service for now. Revisit only if its pricing is confirmed and it earns its cost.

## 3. Public demo is recorded runs, with a local offline mode (2026-10-18)

**Decision:** the public demo is a static site replaying recorded run bundles; live generation is off or rate limited. A one-command local mode works with a fake model client.
**Why:** Rules 4.8 require the project to stay accessible and free to judges until Nov 10, and judges clicking around must not burn the budget.
**Rejected:** an always-on live pipeline as the public default (cost, abuse risk), and presenting cached output as live (the UI labels recorded runs honestly).

## 4. Numbers first, words second (2026-10-17)

**Decision:** a deterministic stats engine computes every figure and finding; agents only narrate those figures; a verifier agent rejects any claim not backed by a finding's evidence.
**Why:** it makes the explanations auditable and testable against the generator's answer keys, which is our main answer to "explainable".
**Rejected:** letting a model read raw events and interpret them directly (unverifiable, expensive).

## 5. Evaluation discipline (2026-10-18)

**Decision:** thresholds are tuned on seeds 1-40 only; bars are checked on held-out seeds 101-120 and fresh seeds 201-220; matching rules, time tolerances and the 80% recall bar are never loosened to make a number pass. Failing bars are marked `xfail(strict=True)` with the real numbers and stated in the README.
**Why:** the answer keys are only evidence if we cannot fit to them. The first run on 101-120 already showed that tuning on six seeds does not generalise.
**Rejected:** tuning on the held-out seeds, widening tolerances, dropping hard phases from the score. Note: the surge, siege and momentum rules were tuned on seeds 1-6 only; the counter-attack rule (entry 7) and the chaos rule (entry 9) on 1-40.

## 6. Public repository from the start (2026-10-17)

**Decision:** the repo is public from the first commit, with small, frequent commits; the link is added to the project page near submission.
**Why:** the Official Rules require a public repo, and a visible history is our evidence that the project is newly built.
**Rejected:** developing privately and publishing at the end. No secrets in git: `.env` is ignored and `.env.example` is kept current.

## 7. Counter-attack rule: shot or box entry, 12 s, and what the held-out runs showed (2026-10-18)

**Decision:** a counter-attack is an open-play regain followed within 12 s by a shot or a completed pass into the box, at most 4 passes and at least 30 m gained. We keep this rule, report its real recall, and do not tune further.
**Why:** the first rule (any shot within 20 s) scored 6/20 on 101-120. Retuned on seeds 1-40 it hits 19/40 (48%), but only 5/20 (25%) on 101-120 and 11/20 (55%) on fresh 201-220, so about 40% pooled held-out. On a per-event basis the planted counters look like ordinary quick transitions; xG and regain-depth cuts lost hits faster than noise.
**Rejected:** loosening the 80% bar or the matching window; accepting a rule that fires 5-8 times per balanced match. Open option, not done: detect counters as a *rate* over a window (a counter spell) instead of single moments.

## 8. Counter-attack work is closed; counters are low-severity context (2026-10-18)

**Decision:** `counter_attack` findings are kept but capped at severity 0.3 (0.1 base, up to 0.3 for a counter that ends in a high-xG goal), below the 0.5 floor (`LLM_TRIGGER_SEVERITY`) at which a finding can trigger a model call on its own. A counter that scores is narrated through its `goal` finding. No more tuning on counters.
**Why:** per-event counters do not separate planted counters from normal quick transitions: 48% when tuned (seeds 1-40), 25-55% on held-out seeds, and about 3 outside planted windows per balanced match. Treating each one as a headline would spend model calls on noise.
**Rejected:** dropping counters entirely (they are still cheap, useful context); raising severity to match how a counter looks; more tuning. Open option, not done: counter *spells* as a rate over a window.

## 9. Chaos spell: 8-minute match window and stricter start (2026-10-18)

**Decision:** match-wide numbers (turnovers, completion, spell length) use an 8-minute window instead of 5. A chaos spell starts at chaos index 0.75 (was 0.8) with a completion part of at least 0.3 (was 0.5), held 90 s at 90% duty, and ends below 0.4. Tuned on seeds 1-40 only, with 101-120 and 201-220 deliberately not run while tuning.
**Why:** on 201-220 the old rule fired on balanced play (balanced spell findings 1.10 per match against a cap of 1.0): 5-minute passing windows are only about 40 passes, so noise looks like chaos. Longer windows cut that without losing the planted spells. On seeds 1-40: comeback chaos 62% to 72%, end-to-end 88% to 88%, balanced spell findings 0.82 to 0.50 per match. The cost is lag: end-to-end median detection +5.5 min (was +4.1), so some hits sit near the +8 min edge.
**Rejected:** loosening the matching window or the 80% bar; a higher chaos threshold alone (with the 8-minute window, 0.9 gave comeback 22/40 and end-to-end 30/40 on seeds 1-40, fewer hits than 0.75 for little extra quiet). Only the match-wide window was lengthened; the 5-minute team windows that siege and surge use are unchanged.
**Outcome (held-out, frozen rule):** balanced spell findings 0.50 on 101-120, 0.50 on 201-220 and 0.45 on fresh 301-320, so the 1.0 cap now holds everywhere (it was 0.70 and 1.10). Chaos recall did not improve: comeback chaos 65% / 70% / 60% and end-to-end 70% / 75% / 80% on 101-120 / 201-220 / 301-320. On the two older ranges combined it fell from 75% to 68% (comeback) and from 80% to 73% (end-to-end), so we traded recall for quiet. The 80% recall bar is met in 1 of 9 storyline results (end-to-end on 301-320, at exactly 80%).
**Decided:** keep the rule (the false-positive fix is real and the recall loss is modest), stop tuning chaos in this milestone, and mark each failing recall bar `xfail(strict=True)` per storyline with the measured numbers, so only bars that truly fail are expected failures. Reaching 80% on chaos will need a different signal, not another threshold or window change.

## 10. Model client: Agent Framework's chat client is the seam; Foundry via the project endpoint (2026-10-19)

**Decision:** we do not define our own model interface. Every agent gets an Agent Framework chat client (`SupportsChatGetResponse`): live, `agent_framework.openai.OpenAIChatClient` (Responses API) on an `AsyncOpenAI` client from `azure.ai.projects.aio.AIProjectClient(FOUNDRY_ENDPOINT, DefaultAzureCredential()).get_openai_client(max_retries=0, timeout=…)`; offline, our own `FakeChatClient` built on Agent Framework's `BaseChatClient`. Budget, concurrency, timeout, retry and usage logging live in one Agent Framework `ChatMiddleware` attached to each client, so they apply to every model round-trip, including tool-call loops. `FOUNDRY_ENDPOINT` is the Foundry *project* endpoint. The default mode is `fake`; live calls need `PITCHSIDE_LLM=foundry`.
**Why:** milestone 3 agents can then be real Agent Framework `Agent`s, unchanged between fake and live. Verified against agent-framework-core 1.22.0 / agent-framework-openai 1.17.0 / azure-ai-projects 2.9.0 and the Learn docs (Oct 2026): `get_openai_client` appends `/openai/v1` and uses scope `https://ai.azure.com/.default`; the OpenAI SDK retries twice by default, and Agent Framework wraps every SDK error in a plain `ChatClientException` with the `openai` error as its cause. A middleware can call `call_next()` again, so retries can live there.
**Rejected:** our own thin `complete()` interface (Agent Framework would only be a transport and the fake would not run real agents); `agent_framework.foundry.FoundryChatClient` (its constructor exposes no timeout or retry setting, so the SDK's hidden retries would make our per-attempt log and budget wrong); keeping the SDK's built-in retries; API keys.
**Also:** `FOUNDRY_API=responses|chat_completions` (default Responses) because we have not yet confirmed that the Luna deployment serves the Responses API; `scripts/smoke_foundry.py` probes both and says which works. `aiohttp` is a dependency because the async Azure SDK pipeline (`azure.ai.projects.aio`, and managed identity in `azure.identity.aio`) uses it as its HTTP transport.

## 11. Spending caps, concurrency and the failure contract (2026-10-19)

**Decision:** before every model-call attempt the guard reserves its worst-case cost (estimated input plus the output cap, `max_tokens`, which it sets to 1024 when the caller has not) against three caps read from env: **$0.10 per match** (`PITCHSIDE_MATCH_BUDGET_USD`), **200 calls per match** (`PITCHSIDE_MATCH_MAX_CALLS`) and **$10 across the whole usage log** (`PITCHSIDE_TOTAL_BUDGET_USD`). A refused call is never sent and is logged as `refused`. Spending is reloaded from the JSONL usage log at startup. At most **4 calls are in flight** across all agents (`PITCHSIDE_MAX_CONCURRENCY`); backoff waits happen outside the slot. Retries: rate limit, timeout, connection and 5xx, up to 3 retries with full-jitter exponential backoff (base 1 s, cap 20 s, never sooner than `retry-after`); auth, missing deployment, bad request and content filter are not retried. Prices fail closed: an unknown price model is a startup error, a response without usage is charged the worst case, and a **timed-out attempt is charged the worst case** because the service may still have billed it (so the log's cost is an upper bound in that case, and says so).
**Caller contract:** every failure is an `LLMError` (`BudgetExhausted`, `ServiceUnavailable`, `RequestRejected`/`AuthFailed`, `MalformedOutput`). Milestone 3 agents catch it and fall back to a deterministic template narrative built from the finding's evidence, marked as such, so offline, over-budget and outage runs still produce output and recorded runs never depend on the service.
**Why:** about 30 detector-selected moments per match times four roles, with verifier retries, is *estimated* at about $0.04 per match at Luna prices (to be replaced by measured cost from the first live runs); $0.10 leaves headroom without letting a bug loop. Reservations stop concurrent calls overshooting a cap. A low deployment quota (tokens per minute) is easier to respect by limiting calls in flight than by retrying 429s.
**Rejected:** checking spend only after calls (concurrent calls could overshoot); logging timeouts as free; a cap shared across processes (the ledger is per process; a deployed multi-replica service needs shared state, planned for Cosmos DB in milestone 6).

## 12. Which findings reach the models, output caps, and run-scoped match budgets (2026-10-20)

**Decision:** a finding goes to the agents only if `can_trigger_model_call` (severity at least 0.5) **and** it is a moment or a spell *start*; spell *ends* always get a deterministic template (they only inherit their start's severity). Measured on seeds 1-10 that is about **4.5 findings per balanced match and 12-13 per storyline match** (not the "about 30" assumed in entries 1 and 11), plus two recaps per match (half-time, full-time). Every role passes its own output cap, which counts reasoning tokens: interpreter 1500, explainer 3000, verifier 1500, personalizer 4000 (`PITCHSIDE_MAX_OUTPUT_<ROLE>`), with Responses API reasoning effort `low` (`PITCHSIDE_REASONING_EFFORT`). A reply cut off at the cap (finish reason `length`) is logged and raised as `MalformedOutput(kind="truncated")`; the agent retries once at twice the cap. The match budget is now kept **per run of a match** (`run_id/match_id`), and offline (fake) runs write their usage log inside their own run directory.
**Why:** the 1024-token default from milestone 2 could truncate JSON once a reasoning model spends tokens thinking. A per-match budget keyed only by match id meant re-recording a match (same seed, same id) started from the earlier run's spending and would quietly fall back to templates; fake costs in the live log would have eaten the $10 total budget after a few offline evaluations. **Recorded demo runs use `PITCHSIDE_MATCH_BUDGET_USD=0.25`** so none of their findings is downgraded for budget reasons; the bundle manifest lists budget fallbacks, and there should be none.
**Rejected:** narrating spell ends with a model call (about 25% more calls for "the siege is over"); one global cap for every role (the personalizer writes 8+ texts, the verifier a short verdict); dropping cost accounting in fake mode (offline evaluation should exercise the cost plumbing too).

## 13. Agent architecture: a graph workflow per job, four roles, no LLM coordinator (2026-10-20)

**Decision:** each model-eligible finding, and each half-time and full-time recap, runs through its own Agent Framework graph workflow (`WorkflowBuilder`): interpreter -> explainer -> deterministic checker -> semantic verifier -> personalizer -> publish, with typed handoff messages on the edges, a bounded retry loop back to the explainer (at most 3 drafts, with the rejection reasons as feedback) and a template fallback. The four roles are Agent Framework `Agent`s, each on its own guarded chat client. A plain-code director (not a model) picks the jobs, freezes their context at detection time, runs them four at a time and merges the results. Per-job working state (ledger, brief, drafts, checks, audit) lives in workflow state; match-level state (all records) is written only by the director. The interpreter calls the stats tools as function tools now; milestone 4 serves the same functions over MCP. A2A is not used.
**Why:** our routing has one correct answer that code can compute (severity, status, checker and verifier results), so a model-driven router would add cost, nondeterminism and a failure mode while deciding nothing. `HandoffBuilder` (agent-framework-orchestrations 1.3.2) hands off through LLM tool calls, is interactive by default and its autonomous mode is experimental. One fresh workflow per job because a `Workflow` instance cannot run twice at once and its state carries over between runs (both checked on agent-framework-core 1.22.0), and because the superstep barrier would make jobs in one run wait for each other. The agent-framework-a2a package is still beta and nothing here needs a remote agent.
**Failure recovery:** interpreter fails -> rule-based brief; explainer fails, or every claim fails the checks after the last draft -> template narrative with the reason; after the last draft only claims that passed both layers are shown; semantic verifier fails -> claims accepted on the deterministic check alone, flagged `semantic_check: skipped: <reason>`; personalizer fails or one of its texts fails the persona checks -> template text for those personas. A budget refusal marks the run so later jobs go straight to templates. Faults can be injected on purpose (`--inject-faults`, opt-in) to show each path; injected faults are listed in the run bundle.
**Rejected:** an LLM coordinator or planner agent (about 15-20% more calls, nothing to decide); `HandoffBuilder`/`SequentialBuilder`; one workflow run for a whole match (superstep barrier, shared-state races); the experimental functional `@workflow` API; showing claims only the deterministic layer has seen without saying so.

## 14. Structured claims, one personalizer call per moment, recaps, and how agent output is scored (2026-10-20)

**Decision:** the explainer returns claims, each citing ledger ids and listing every number it uses; a claim is shown only if it passes the deterministic checker (and the semantic verifier, unless that was unavailable, which is flagged). One personalizer call per moment writes every persona (analyst, casual fan, a favourite-player view for one featured player per club) in every language (English and Spanish), with numbers kept as digits so the checker verifies every language; a failing text is replaced by a template text, not retried. Half-time and full-time recaps (Rules 4.1 iii: recaps, milestones, player-performance context) are built from the claims verified earlier in the match plus totals and player numbers, through the same explainer -> checker -> verifier flow. `pitchside eval-agents` scores runs against the answer keys: planted phases and goals covered (with the scoring club and the score), recaps, first-draft deterministic grounding, semantic rejections, unsupported claims before and after the verifier, injected bad drafts caught, fallbacks by reason, and cost per match. Prompts may be iterated on seeds 1-40; the live evaluation is reported on held-out seeds 201-205.
**Why:** batching personas and languages keeps the call count at about 5 per moment; a translator per language would double it. "Unsupported after the verifier" is 0 by construction because the checker is the gate, so the report says so and a live run writes a spot-check file of shown claims for a person to judge. Offline numbers come from fake agents that are correct by construction, so the report and the README label them a plumbing check, not model quality; the meaningful offline numbers are the injected-fault ones. Estimated cost (Luna prices, to be replaced by measured cost): about $0.0023 per moment, $0.015 per balanced match, $0.03-0.04 per storyline match.
**Found while building the evaluation:** injected corruptions exposed a checker gap (a claim about one club backed only by match-wide numbers passed); fixed, and a minute "outside the window" corruption that was in fact inside a recap's whole-match window was corrected to a minute after the moment. With those, 42 of 42 corrupted drafts are caught on seeds 1-3.
**Rejected:** free-text narratives checked by a model alone (unverifiable); one call per persona or per language; Azure AI Translator for now (an optional milestone-6 swap: free tier, one more Azure service, but a second step to verify); scoring narratives by eyeballing.

## 15. The stats engine as a read-only MCP server; the SDK stays on 1.x; the host owns the time bound (2026-10-20)

**Decision:** `uv run pitchside mcp` serves the stats engine as twelve MCP tools (possession, field tilt, pressure, passing, shots and xG, momentum, control vs chaos, key moments, evidence lookup, match totals, recent window, list matches), all `readOnlyHint`, with typed inputs and outputs, over stdio (default) or Streamable HTTP (`--stateless --json-response --allowed-host` for Container Apps; designed and checked locally over a real socket, not deployed). **Every stats tool requires `as_of_s`** and computes only from events at or before it; an optional `as_of_event_id` can only tighten the bound. The bound is enforced in one place (`stats/timeline.py`: the only read path is `as_of()`), and tested by replacing everything after the bound with another match and requiring identical answers from every tool, directly and over the protocol, and by checking that no timestamp in any response is after `as_of_s`; breaking the bound makes the tests fail. `PITCHSIDE_TOOLS=local|mcp` (default `local`) switches the interpreter. In `mcp` mode the interpreter uses Agent Framework's `MCPStreamableHTTPTool` against the real server running in-process behind the real Streamable HTTP transport (in-memory ASGI, no sockets or subprocesses), or against a deployed server when `PITCHSIDE_MCP_URL` is set. **The host, not the model, sets the bound**: a function middleware overwrites `as_of_s`, `match_id` and `as_of_event_id` from the job on every call, so a model that asks for `as_of_s=99999` or another match is overridden (Agent Framework validates arguments after middleware, so a model that omits the required bound is fine too).
**SDK version:** the server uses the MCP Python SDK **1.x** (`FastMCP`), pinned `mcp>=1.24,<2`. SDK 2.x (latest 2.3.0) renames `FastMCP` to `MCPServer`, but agent-framework-core 1.22.0, the latest release, declares `mcp<2` and fails on 2.x (verified: `'InitializeResult' object has no attribute 'protocolVersion'`; it reads `protocolVersion`, `isError` and `McpError`, which 2.x renamed). The interpreter needs Agent Framework as its MCP client, so both sides stay on 1.x. Moving to 2.x later is an import and constructor change in `mcp_server.py`, once Agent Framework supports it.
**Ledger check:** with function middleware an MCP result arrives as a list of text content holding the tool's JSON, which is what the ledger recorder already unwrapped, so `c*` ids and quotes are assigned to MCP numbers exactly as to local ones. What did not work was the recorder replacing the whole result with `{"items": ...}`, which would have dropped `key_moments`' moments; it now swaps only the numeric `items` for id-bearing ones (commit d542e3c) and passes the rest through. A test runs the same matches in both modes and requires identical ledgers, drafts, checks, narratives and audit trails (apart from the interpreter's prompt digest, since its tool list differs), including against a remote server. Jobs now carry `as_of_event_id`: one finding in seed 1 is detected on an event that shares its clock reading with a later event, so a time-only bound would have returned a slightly different snapshot than the one the job froze.
**Cost:** eleven tool schemas add about 2,800 tokens to every interpreter call, about $0.0003 at Luna input prices, so roughly $0.005 per storyline match on top of the estimates in decision 14 (measured token count; the dollar figure is an estimate until a live run). If a live run shows the small model misusing the tools, narrow `INTERPRETER_TOOLS` in `agents/mcp_tools.py`.
**Rejected:** a stdio subprocess for the pipeline (a process per match, and the match would have to be written to disk first; stdio stays for external clients); letting the model pass the bound (it can ask for the future, and the server cannot tell who is asking); write tools or match upload over MCP (read-only is the point); a 2.x server with a hand-written client for Agent Framework (we would lose the middleware and tool loop we test against); exposing all twelve tools to the model including `list_matches` (the host pins the match); making the local tools the full set too (a smaller tool surface is cheaper and easier for a small model; local keeps the two composite tools).

## 16. The overlay contract: a derived file on a replay timeline, with conflicts resolved at build time (2026-10-22)

**Decision:** each run bundle gets `overlay.json` (bundle format 1.1), built in Python from the bundle's other files (`pitchside.render.overlay`, schema in `docs/overlay.schema.json`, CI fails if stale; described in `docs/OVERLAY.md`). Overlay times are on a **replay timeline**: the match clock plus a 45 s half-time segment and a 45 s full-time segment, so the half-time recap plays in the break instead of over the first 45 s of the second half (the bundle's clock has no break: half-time is exactly 2700 s). Lower-third conflicts are resolved when the file is built (one at a time; higher priority pre-empts; equal or lower waits up to 8 s, else side panel only; spell ends and counter-attacks side panel only), so a renderer only checks `show_at_s <= t < hide_at_s` per placement. Each overlay carries its evidence chain: claim -> ledger number (metric, window) -> events, where `triggering` (the finding's own `event_ids`) and `in_window` (a stored, deterministic filter of the events the metric is computed from) are separate relations; and its audit trail condensed into steps, rejected claims, injected faults, a call summary and badges. Club colours and crest patterns are generated from the team id (fixed hue spread, contrast-checked, kept off the UI's amber, home and away at least 60 degrees apart). `hold_ms` asks a fast replay to pause briefly at a lower-third start so it can be read.
**Why:** a half-time recap timed on the raw clock covered live play; resolving placement in Python means the rules are tested once with the rest of the pipeline and every consumer (the web UI, any later renderer) agrees. Finding evidence only records event ids per finding, and spells often record none, so "the events behind this number" has to be derived; labelling it `in_window` keeps the UI from presenting a window's events as the cause. The bundle files stay the source of truth: the overlay is rebuilt from them (`pitchside overlay <dir>`), and a test checks a written overlay equals a fresh build.
**Rejected:** keeping the bundle's match-clock `display` times (the recap overlap); resolving conflicts in JavaScript (a second implementation to test); storing event ids per evidence item in the stats engine (a change to milestone 1 for a display need); real or real-looking club colours.

## 17. The web UI: a static site with no build step, a pure replay engine tested in V8, honesty labels from the manifest (2026-10-22)

**Decision:** `web/` is plain HTML, CSS and ES modules with self-hosted OFL fonts and no external requests, deployable as-is to Azure Static Web Apps Free (`web/staticwebapp.config.json` sets the `.jsonl` MIME type and a strict CSP). `uv run pitchside serve` is a standard-library server with explicit MIME types. The replay logic lives in three pure modules (`replay.js`: timeline mapping and a clock that takes wall time as an argument, with play, pause, seek, speed and holds; `timeline.js`: everything on screen derived from `t` by binary search, so seeking backwards equals playing forwards; `honesty.js`: badge strings), and `tests/test_web_js.py` runs them in V8 through `mini-racer` (dev group) inside the normal test suite, cross-checked against the Python builder and the event stream. The badge is chosen from `pipeline.llm_mode` only: "Recorded run generated by the live pipeline" for `foundry`, "Offline demo (fake model client)" for `fake`, "Unverified run" if the mode is unknown or the overlay disagrees with the manifest; the manifest's own label is shown verbatim in the run info panel; injected faults get their own badge, also in clean mode. The broadcast view shows one persona (a broadcast has one audience); the analyst dashboard shows analyst, casual and favourite-player texts side by side. Sample runs in `web/data` are offline (fake client) and regenerated by `pitchside demo-data`; exactly one has faults injected (a test checks this and that the index says so). Sparklines are drawn only up to the current moment, so the replay does not show the future.
**Why:** nothing needs bundling, and a second toolchain (Node) on a solo Windows setup costs more than it gives. mini-racer installed cleanly (py3-none wheels for Windows and manylinux) within the 15-minute time box agreed for it; the fallback was testing the same modules through Playwright, not Node. Deriving state from `t` instead of updating it incrementally is what makes scrubbing back and forth trivially correct and testable.
**Rejected:** a framework or bundler (React/Vite); CDN-hosted fonts or libraries (network dependence, reproducible screenshots); Node's test runner; personas in tabs only (the difference between them is the point and should be visible at once); taking the badge text from the manifest label (the badge strings are fixed so they cannot drift).
**Revised after review (2026-10-23):** text sources are named from the manifest too: "Offline stand-in" for the fake client, the role's deployment name for a Foundry run, never a bare "Model" (`honesty().sourceLabels`). The drawer says "verified claims" only when the checker and the semantic verifier both passed, otherwise "checked claims (semantic check skipped)" or "(template: semantic check not run)". The lower-third hold is about 6 s of real time (`hold_ms` 6000, recaps 9000; was 2.5-4 s). In clean mode the broadcast stage fills the viewport with larger lower-third text; at 1920 x 1080 the analyst dashboard fits without scrolling (three columns).

## 18. Azure hosting: one resource group in Bicep, a static demo, an IP-restricted MCP server, no identity yet (2026-10-23)

**Decision:** `infra/main.bicep` (plain Bicep, deployed by `infra/deploy.ps1` with the Azure CLI; no azd) defines one tagged resource group: Azure Static Web Apps **Free** (`westeurope`) for `web/` and the recorded runs; an Azure Container Apps environment (Consumption workload profile, `swedencentral`) with the MCP server app (0.25 vCPU / 0.5 GiB, replicas **0..1**, `/healthz` probes, the three published matches preloaded); Log Analytics for its logs (1 GB/day cap, 30 days); a Cost Management budget with e-mail alerts. The image is built by GitHub Actions and pushed to **GHCR as a public package** (no registry, no credentials; new packages start private, so making it public is a documented step). The site is published by a manual GitHub workflow with `Azure/static-web-apps-deploy@v1` and `skip_app_build` (no Node), so freezing `main` cannot change the demo. **Protection:** an ingress IP allow-list (only the owner's address) plus an in-app rate limit (`pitchside.ratelimit`: 120/min per client, burst 60, 300/min overall, 429 with `Retry-After`; per client by the last `X-Forwarded-For` hop) and the existing Host allow-list; no keys anywhere. **No managed identity or role assignment:** nothing deployed calls a model (the live recording runs on the owner's machine under `az login`, using the deployed MCP server), so an identity would be unused privilege; a cloud recorder (Container Apps Job + user-assigned identity with Cognitive Services OpenAI User) is documented as planned. `deploy.ps1` runs in five idempotent stages (preflight, providers with live region checks, group, what-if then deploy, verify) and resumes with `-FromStage`; `teardown.ps1` refuses to run before 2026-11-11.
**Why:** a static replay costs nothing and cannot be abused; the MCP server is the one cloud component the agents really use, so it is the one worth hosting, and it must not be an open endpoint. Container Apps has no built-in request rate limiting, hence the middleware; one replica keeps its in-memory buckets global. Verified against the official docs (2026-10-23): the 0.25 vCPU / 0.5Gi combination, the Consumption free grant (180,000 vCPU-s, 360,000 GiB-s, 2M requests per month) and zero charge at zero replicas, `ipSecurityRestrictions`, the Bicep API versions (`containerApps`/`managedEnvironments@2026-07-01`, `workspaces@2026-03-01`, `staticSites@2025-03-01`, `budgets@2026-06-01`), the Static Web Apps Free limits (250 MB, 15,000 files, 100 GB), the role GUIDs, the `az` flags the scripts use, the uv Docker pattern and GitHub's action pins. **Measured:** with 23 matches preloaded the server took about 63 s to start at 0.25 vCPU (longer than the pipeline's 30 s MCP request timeout after a scale-from-zero), with the three published matches about 15 s and 89 MiB, so only those are preloaded; a test checks they cover every run in `web/data`.
**Rejected:** azd (more conventions and tooling for one template); Azure Container Registry (a monthly charge for an image that can be public); Entra ID built-in auth on the MCP server for now (app registration plus app-role checks in code for a read-only, synthetic-data server; planned); a managed identity without a workload that uses it; API Management for rate limiting (cost and setup); Application Insights in this milestone (the new `microsoft-opentelemetry` distro is a heavy dependency; logs and platform metrics cover the demo; planned); Cosmos DB, Event Grid, Functions, Translator and Speech (no consumer in a static replay; Translator was already rejected in decision 14). The Static Web Apps region is not hard-coded against a list because no official list is published: `westeurope` appears in Microsoft's own Bicep sample, and `deploy.ps1` checks it with `az provider show` before deploying.

## 19. No Luna quota on the trial subscription: gpt-5-mini is the working model (2026-10-23)

Luna stays the target: if quota arrives, the deployments and `PITCHSIDE_PRICE_MODEL` switch back and nothing else changes. Decision 1 otherwise stands: one small model for every role, no Sol. Price table version `2026-10-23` adds gpt-5-mini at **$0.25 in / $0.03 cached / $2.00 out** per 1M tokens: the Azure OpenAI pricing page lists EUR 0.22 / 0.03 / 1.76 for Sweden Central Global, converted at the page's rate of 1 USD = 0.88 EUR (input and output convert exactly; cached converts to 0.034 and is recorded as 0.03). The default per-match budget (`PITCHSIDE_MATCH_BUDGET_USD`) rises from $0.10 to **$0.25**, the value already used for recorded runs.

With `PITCHSIDE_REASONING_EFFORT=off`, gpt-5-mini reasons at its default, `medium`, and costs more.

## 20. The checker rejects a number joined to the word before it (2026-10-23)

**Decision:** a new deterministic reason, `glued_number`: a claim or persona text fails when a number is written straight after a letter ("it is0-1", "a0.31 xG"), with feedback naming the fix ("write \"is 0-1\" with a space"). Claims go back to the explainer as with any other reason; persona texts fall back to their template. Ledger ids written in the text ("e1") are exempt.
**Why:** the first live smoke test on gpt-5-mini showed claim text "it is0-1." and an interpreter angle with "aftera". Neither came from our code: Agent Framework copies each Responses `output_text` verbatim, `json.loads` keeps it, and the smoke script prints it unchanged, so the spaces were missing in the model's reply. Beyond the looks, it was a checker gap: the number scan ignores digits that follow a letter, so "a0.48 xG" would have passed with no number check at all. The score pattern happened to catch "is0-1".
**Rejected:** inserting the space ourselves after verification (the shown text would no longer be what the model wrote and the checker saw); a dictionary check for merged words like "aftera" (no deterministic rule without false positives; the semantic verifier and the spot check are where a person-visible wording problem is caught).

## 21. One club name per sentence, yes/no facts in words, chaos windows named (2026-10-24)

**Decision:** wording only; no checker rule changes. (1) The explainer and personalizer prompts now state the rule the checker enforces: a number belongs to the club or player named last before it in its sentence (else the one named after it, else the claim's `team_id`). So a club is named once, before its first number, and again only to switch clubs, never between a word and its number. The old rule "name the club right before each of its numbers" is gone. The `team_mismatch` feedback now says which club the checker read and how ("the club named last before it in this sentence is Aurora Rovers; name Ironvale Athletic before this number"). (2) Yes/no facts (`possession_won_in_open_play`, `ended_with_shot`) are phrased in words with no digit, in English and Spanish ("ball won in open play" / "possession began from a restart or a save"). Their evidence lines show `yes`/`no` instead of `1 count`, and a claim cites them in `refs` with no number. (3) In finding ledgers, the four match-wide rolling chaos numbers (`chaos_index`, `turnovers_per_min`, `pass_completion`, `mean_spell`) name their window ("79% pass completion in this spell"); templates and tool results keep their own phrasing. Evidence lines say `both clubs`, not `match`, for match-wide numbers.
**Why:** a read-only analysis of live evaluation `20261024T063706Z-f0cd52` (seeds 201-205). 70 of 582 shown claims, and about one persona text in five, put a club name between a word and its number ("from Aurora Rovers 4 m", "his Aurora Rovers 2nd goal"). 12 shown claims and 23 persona texts quoted the open-play flag as "(1)". One shown claim read the chaos window as the whole match ("Match pass completion is 79%", copied from the `match` column), which clashes with our own vocabulary, where "in the match" means since kick-off. Probing the unchanged checker showed clean phrasings pass and misattributed ones still fail, so the prompt rule was stricter than the check needs; new tests pin both sides. `opponent_pass_completion` was checked on the way and is correct (the pressed club's own window figure, labelled with that club, 22/30 = 73.3% at the emitting event in `aur_irv_end_to_end_0201`); a regression test now pins it.
**Evaluation discipline:** these problems were found by reading seeds 201-205, but nothing was fitted to their numbers (no threshold, cap or matching rule). The change is measured once on seeds 206-210, also held out, and is not adjusted from that result. Offline evaluation on seeds 1-40 is a plumbing check.
**Rejected:** a deterministic check that rejects a club name wedged before a number (more retries and cost for a wording problem the prompt can fix; revisit if seeds 206-210 still show it); naming the window by its length ("over the last 8 minutes": the 8 is not a ledger number, so the checker rejects it, as it rejected "81:01–89:01" in one live retry); removing club names after verification (the shown text must be what the checker saw, as in decision 20).

## 22. Goals carry their scoreline, the checker reads minutes and clock times, output caps from measured use (2026-10-24)

**Decision:** (1) Every goal finding gets a `goal_margin` evidence number: the scoring club's margin after the goal (baseline: before it). The stats engine computes it at the goal's own event, so like every finding number it cannot see later play. The ledger quotes it with what the goal did and the score, decided by code from the margin (opener, equaliser, ahead, extend, back): "Aurora Rovers equalise: Aurora Rovers 1-1 Ironvale Athletic". The scorer's goal count reads "goals 2, including this one". The explainer prompt asks each goal for one claim that gives the score and cites `goal_margin`, and asks that "equalised", "went ahead" and the like cite it too. The verifier prompt says such claims are supported by that evidence. `score_mismatch` is unchanged: a written score must still be one the match has had, cited or not. (2) The checker reads clock times ("70:12", "81:01–89:01") as times and checks them against the window, never as numbers or a score. "N minutes" / "N min" / "N minutos" counts as the match minute when N is the job's own minute; any other value stays a duration and must be cited. "Nth minute", "minute N", "minuto N" and "N'" were already read. (3) Default output caps: interpreter 1500 (unchanged), explainer 3000 → **3700**, verifier 1500 → **2400**, personalizer 4000 → **4200**. Each is at least twice the largest output measured live, reasoning included (588 / 1824 / 1138 / 2045 tokens), the smoke script's headroom rule.
**Budget check (worst case):** the guard holds the estimated input plus the cap for every call. With the largest inputs seen live, that is $0.0037 / $0.0082 / $0.0051 / $0.0086 per call. Four calls in flight, all on a truncation retry at twice the cap, hold at most $0.068. On top of the most expensive match measured live ($0.139), the peak is $0.21, inside the $0.25 match budget; a test pins this. If every call used its whole cap, a match would cost up to about $0.50 (mean $0.36). In that case the match budget, not the caps, is the bound: the remaining moments fall back to templates.
**Timed-out calls (reported, unchanged):** they are logged as `status: error`, `error_kind: timeout`, with no token counts, and charged the call's worst-case hold. That charge counts toward the match budget and every cost total (`pitchside cost`, evaluation reports, bundle manifests). On seeds 201-205 there were 10 timeouts at 20 s, charged $0.0708 of the $2.0186 recorded (3.5%), and each guard retry succeeded. The Azure OpenAI FAQ says a request is billed if the service did any processing, even when the status is not 200 (a time-out is its example), and our records cannot show whether it did. So the worst-case charge stands as the conservative figure; Cost Management shows the real one.
**Why:** the same live run as decision 21. 20 of its 54 semantic rejections were about a score, an equaliser, a winner or a shot's outcome missing from the cited evidence. 5 of 67 goals stated no score at all, and only 13 shown goal claims stated one. 11 of the 12 persona texts replaced for `unlisted_number` had written the job's own minute in a form the checker did not read. One retry failed because "81:01–89:01" was read as numbers and as the score "1-89". The verifier used 76% of its cap.
**Evaluation discipline:** as in decision 21. Nothing was fitted to seeds 201-205; the caps follow a fixed rule (twice the largest output), not a tuned value. The change is measured once on seeds 206-210.
**Rejected:** scoreline evidence for big chances and recaps in this change (only goals were in scope; big-chance rejections such as "they still trail 1-0" stay, a follow-up if seeds 206-210 show them); accepting any number before a minute word inside the window as a minute (an invented "20 minutes of pressure" would pass); telling the verifier that every shot in a goal job is the goal (broader than needed, since citing `goal_margin` covers it); raising the interpreter cap (39% used).

## 23. Labels that survive being pasted, a goal must state its score, rejected persona texts kept (2026-10-24)

**Decision:** (1) Ledger labels are written to read right when a model pastes them verbatim, inside a sentence or as one:
- the scorer's tally is a clause ("Rafa Yaldiran has 2 goals in the match, including this one"; "this is Rafa Yaldiran's first goal of the match"), as are the other player numbers ("has 5 shots in the match");
- the pressed club's figure reads "Aurora Rovers are completing 73% of their passes";
- counts of one are singular ("1 pass in the move");
- a possession that did not begin in open play names its real cause, read from its `PossessionChangeEvent` ("gained possession from a goal kick", "from a kickoff", "after the ball went out of play", "from a save by their goalkeeper"), and its clock reads "after gaining possession", not "after winning the ball".

(2) The scoreline puts the score first: "it is 1-1: Aurora Rovers equalise". The scoring club is the last club named, so a number pasted after it is read as that club's. When two listed numbers have the same value, the checker now prefers the one whose ledger number it matches. A score digit listed under `goal_margin` beside a scorer's tally of the same value no longer takes the tally's place. The chosen listing must still pass every check.

(3) A goal job's shown claims must include one that cites `goal_margin` and states the score. The rule is applied after the checker and again after the verifier, since a dropped claim must not take the score with it. A draft without it goes back with "state the score: … cite e10"; on the last attempt the job falls back to the template, whose claim states the score and now cites `goal_margin`.

(4) The personalizer's rejected text is stored in the audit entry (`data.replaced[].text`). The overlay and the UI never read it.

(5) Window labels:
- the match-wide chaos numbers are combined figures ("3.0 turnovers per minute across both teams in this spell");
- one club's rolling counts and sums (`shots`, `xg`, `tackles_won`, final-third passes) name their window in spell findings ("3 shots in this spell");
- in tool results they name it as "in the last few minutes", or "in that spell" for an earlier finding's numbers.

A label names at most one window, in words. The explainer and personalizer prompts gain one line each on combined figures, and the explainer one line on naming a window once and not listing a score's digits. The club-once rules are unchanged.

**Why:** the read-only analysis and spot check of the live evaluation on seeds 206-210:
- 61 of 627 shown claims pasted "goals N, including this one" ("it is his goals 2, including this one"), and 20 pasted "restart or a save".
- One shown claim called a save "restart-originated" (spot check B #12).
- 5 of the 7 first-draft checker failures came from the new decision-22 phrases: the scoreline named the away club last (balanced_0206, siege_0210), and score digits were listed as numbers (comeback_0208).
- 10 of 70 goals cited `goal_margin` but gave no score, since nothing checked it.
- Spot checks B #14 (a 5-minute window's "3 shots and 0.85 xG" read as match totals) and #20 ("both teams averaged") were scope readings, not wrong numbers.
- The rise in persona `team_mismatch` (decision 21 follow-up) could not be diagnosed because the rejected text was not kept.

The brief's "between the two teams" became "across both teams": "two" is a number word, so the checker would read it as an unlisted 2. For the same reason no label holds a duration.

**Tests:** every ledger label of six offline matches, pasted as a sentence, passes the checker. Exact strings for every rewritten label in both languages. The two live failures as regressions, next to the old shapes, which still fail (`team_mismatch`, `number_mismatch`). The goal rule on the checker, the explainer retry, the last-attempt fallback and a verifier that drops the score claim. The stored rejected text, kept out of the overlay.

**Evaluation discipline:** these issues were found by reading seeds 206-210 and the spot checks; nothing was fitted to their numbers. Validated offline on seeds 1-40 (a plumbing check). The next live measurement uses a held-out block not yet read, for example seeds 301-305.

**Rejected:** relaxing attribution for club names inside a scoreline (persona texts have no `team_id` to fall back on, so a misattributed number there would go unchecked); a new `ReasonCode` for the goal rule (a schema change for a job-level rule, which is recorded in the audit step and its feedback instead); showing the rejected persona text in the evidence drawer (a reader could take it for shown output; the audit trail is where it belongs).


## 24. A shot's outcome is evidence; the score is a clause; no records beyond the match (2026-10-24)

**Decision:** (1) Every goal and big-chance ledger carries a `shot_outcome` item, read from the finding's own shot event (the event that emitted it, so nothing after `as_of_s` can leak in). It is a word fact like the yes/no flags: stored as an index into off target, blocked, saved, goal; shown to the models as the word ("saved"); labelled "the shot was saved", "the shot was blocked", "the shot went off target", "the shot went in" (Spanish: "el portero detuvo el tiro", "el tiro fue bloqueado", "el tiro se fue fuera", "el tiro acabó en gol"). The MOMENT line of a shot job adds "| outcome: saved", because the personalizer sees only that line and the verified claims. The explainer, personalizer and verifier prompts say an outcome is described only in those words, with no woodwork, header, foot or "conceded" unless the evidence says so. The item is built in the ledger, not the detector, so `findings.json` and every MCP tool result are unchanged.

(2) The checker never matches a digit to a word fact (a flag or an outcome): "outcome 3" or "open play (1)" is now `number_mismatch` in claims and `unlisted_number` in persona texts. Before, a "1" citing a flag would have matched its stored value.

(3) The MOMENT line gives the score as a clause, "score: it is 0-0" or "it is 1-0 to Aurora Rovers" (home goals first), instead of "score Aurora Rovers 0-0 Ironvale Athletic". The scorer's tally reads "this is Rafa Yaldiran's first goal in this match" and "has 2 goals in this match, including this one". The three prompts forbid club, season or career records ("first goal for the club", "debut", "this season"): the evidence covers this match only.

**Why:** a check of the three recorded demo bundles (seeds 7 comeback, 3 siege, 4 end_to_end, live, 2026-10-24). Every cited number recomputed, but the text added what the evidence did not hold: "Rafa rattles the bar" for a blocked shot (a headline), "Westmere Town conceded" after a save, "heads Ironvale in front" (shot events carry no body part), "his first goal for Harbourton City" in a claim the verifier passed and in five persona texts, and "score Harbourton City 0-0 Westmere Town" pasted into all four English texts of a moment.

**Deployment:** client-side only. The MCP server runs the stats engine and tools, which this decision does not touch; the deployed image (built from `90ee028`) can stay.

**Tests:** every goal and big chance on four offline matches carries its shot's outcome, bounded by detection, all four outcomes seen; outcome labels hold no digit in either language; a digit citing a word fact fails in claims and persona texts; the MOMENT line has the score clause and the outcome, and no "Home h-a Away"; exact tally strings. The existing paste-every-label test now covers `shot_outcome`.

**Evaluation discipline:** found by reading the recorded demo bundles, not by tuning on held-out numbers; validated offline on seeds 1-40 (a plumbing check). No live evaluation was run on this change.

**Rejected:** adding the outcome to the detector's evidence (it would change `evidence_lookup` results and need a new server image for one fact the client already has); a numeric outcome the models could quote.

## 25. A recap says what is true at the whistle (2026-10-24)

**Decision:** (1) A recap repeats an earlier verified claim only if every number it cites is fixed at its own moment: a shot's xG, distance and outcome, the goal's margin, the time since gaining possession, passes in the move, metres gained, how the possession began (`POINT_METRICS`). Claims citing window figures (field tilt, possession, momentum, pressures, tackles, a spell's shots and xG, the chaos figures, the pressed club's pass completion), totals so far or player tallies are left out of EARLIER and their numbers are not copied. The recap's own totals and player numbers are computed at the whistle, as before.

(2) A copied goal margin is retold in the past tense: "made it 1-0: Harbourton City opened the scoring" (Spanish "puso el 1-0: …").

(3) Each recap ledger starts with a `recap_score` item, the score at the whistle as a word fact: "it is 1-0 at half-time: Harbourton City lead", "it is 1-1 at half-time", "it ends 2-1: Harbourton City win", "it ends 2-2: a draw".

(4) The checker: in a recap, a score given as the current one ("it is 1-0", "it's", "now 1-0"; Spanish "va", "está", "ahora") must be the score at the whistle, else `score_mismatch` with the feedback "at the whistle it is 1-1; an earlier goal \"made it 1-0\"". Claims and persona texts alike; other jobs are unchanged. The explainer, personalizer and verifier prompts say the same, and the personalizer is told not to narrate an earlier goal as if it just happened ("puts … ahead"); that last part is a prompt rule only.

**Why:** the check of the three recorded demo bundles: the siege half-time recap gave the 19'-24' siege window's 88% field tilt and 72% possession as the half's (first-half possession was 50.7%); the end-to-end half-time recap said "Xarno Uusitalo has 2 shots and 0.37 xG", his numbers at 35' (3 and 1.03 at the break); and the 301-305 evaluation found 3 of 46 recap claims giving an earlier goal's "it is 1-0" as the current score.

**Deployment:** client-side only (ledger, checker, prompts); the deployed MCP server image can stay.

**Tests:** the three demo matches replayed offline (same seeds, storylines and clubs, so the same events): recap ledgers hold only point facts from earlier claims, player numbers end at the whistle, goal margins are told in the past, and each recap's own score is right; the siege half-time has no spell figures; the end-to-end half-time gives the scorer 3 shots and 1.03 xG. The checker rule for claims and persona texts in both languages, its feedback, and that it does not apply outside recaps; an explainer draft with a stale "it is 0-0" is sent back and fixed.

**Evaluation discipline:** found by reading the recorded demo bundles and the 301-305 evaluation; validated offline on seeds 1-40 (a plumbing check). No live evaluation was run on this change.

**Rejected:** recomputing an earlier claim's window figures at the whistle (a spell's numbers have no meaning at the whistle; the recap's own totals say what is true then); a deterministic check for "puts … ahead" (tone, not a number or a score).

## 26. A deterministic guard against invented details (2026-10-24)

**Decision:** The checker rejects details no evidence in this pipeline can hold, with a new reason code `invented_detail`, in claims, headlines and persona texts:
- the woodwork ("the bar", "the post", "crossbar", "woodwork"; Spanish "larguero", "poste", "palo");
- body parts ("header", "headed home", "heads Ironvale Athletic in front", "volley", "left-footed", "backheel"; Spanish "de cabeza", "cabezazo", "volea", "zurdazo"), since shot events record none;
- club, season or career records ("for the club", "first goal for Harbourton City", "debut", "this season", "career"; Spanish "para el club", "primer gol para …", "debut", "esta temporada").

Each language holds its own list in `languages.py`; club names are filled in per match. Not on the list, by decision: "conceded" and tone words ("rattles", "gilt-edged", "spurns"). A rejected claim is retried with the feedback; a rejected persona text is replaced by the template, as for any other check. The headline gets the same check: an invented headline is sent back with "headline: invented_detail: …", and on the last attempt the template's headline replaces it (recorded in the check step's audit detail).

**Why:** the check of the three recorded demo bundles: "Rafa rattles the bar" (a headline, for a blocked shot), "heads Ironvale in front", and "his first goal for Harbourton City" in a claim the semantic verifier passed and in five persona texts. Prompt rules alone (decision 24) did not stop the verifier from passing it.

**False positives:** before shipping, the guard ran over every committed `web/data` bundle at the last 12 commits that changed it (6,912 shown texts), the offline evaluation on seeds 1-40 (35,876 texts), every template narrative and every ledger label of seeds 1-40 × 4 storylines plus the three demo club pairs (33,840 and 33,392 texts), and every phrase in the language tables (264): no hit. On the git-ignored live runs (201-210, 301-305 and the three demo bundles, 14,248 texts) it found 37 hits; 36 are invented details (14 woodwork, 3 volleys, 1 header, 18 club records) and one was a false positive, "una señal de control para el club de Alden Brannholt" ("for Alden Brannholt's club"), now excluded ("para el club de", "for the club of"). The "Nth goal for <club>" form also catches "his second goal for Aurora Rovers" in live claims: ambiguous within one match, and now rewritten as "in this match".

**Schemas:** `ReasonCode` gains `invented_detail`; `docs/run_bundle.schema.json` and `docs/overlay.schema.json` regenerated (one enum value each).

**Deployment:** client-side only; the deployed MCP server image (built from `90ee028`) can stay.

**Tests:** live inventions caught in both languages, near misses passing ("headed into the break", "para el club de …", "first goal in this match"), no phrase of the tables tripping it, claims and persona texts rejected with the reason, an invented headline sent back and fixed, one invented on every draft replaced by the template's, an invented persona text replaced.

**Evaluation discipline:** the word list comes from the demo bundles and the live evaluations' text, not tuned on held-out numbers; validated offline on seeds 1-40. No live evaluation was run on it.
